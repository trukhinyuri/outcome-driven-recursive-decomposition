# State journal version 2

Version 2.0.0 fixes a stale-evidence defect in the optional state tool. If a consumer depended on a replaced branch, later changes to the replacement could restore the consumer's `complete` status without new consumer evidence. A fresh root observation could then produce `mission_verified: true` while those dependent observations were stale.

The invalidation graph now resolves dependency replacements in the same way as completion checks. Revision, new evidence, child addition and further replacement invalidate the affected consumers, their descendants and downstream outcomes. Unrelated branches retain their proof; explicit block/reject decisions remain in force.

## Existing journals

This release changes the state format and uses a major package version. New journals start at schema 2, with the starting version included in the hashed initial event. Version 1 journals are still inspectable, but cannot claim current verification or accept ordinary writes until an explicit upgrade.

`upgrade STATE --reason TEXT` appends one event; it preserves the old event objects and hashes, original requirements and control decisions. It invalidates the proof revisions of all active nodes, so actual checks and fresh evidence are required before completion. The starting header is preserved to replay old events with their original rules. Do not edit the header to change versions. See the [upgrade instructions](../skills/outcome-decomposition/references/state-tool.md#upgrade-version-1-journals), including how to keep a copy for rollback.

## Executed checks

- All 23 existing unit tests passed, plus 10 new regression tests: 33 total.
- Three independently prepared counterexamples reproduced the defect on commit `b976abb` and passed on the fixed candidate: replacement revision, replacement evidence and a chained replacement to an already-verified node.
- A separate CLI-only acceptance harness passed eight groups: real legacy journals, rejected legacy writes, upgrade and fresh recovery, controls and original requirements, header/version consistency, malformed upgrades, forged completion and subsequent invalidation. It checked 16 malformed upgrade variants and verified that rejected operations did not modify state.
- Historical event objects/hashes and the inspected source/fixture files were compared before and after the acceptance runs. The old history was preserved; test copies alone were modified.

Regression fixtures in `tests/fixtures/` are synthetic journals created by the previous implementation. Run the portable regression suite with:

```sh
python3 -m unittest discover -s tests -v
```

The state-engine SHA-256 and machine-readable results are in [the verification record](state-v2-2026-10-02.json). These checks establish the recorded local invariants. They do not prove that an entered observation is true, that a real mission is complete, or that this plugin outperforms another model or method. The skill prompt and automatic invocation policy are unchanged; earlier model smoke observations remain separately dated in [validation.md](validation.md).
